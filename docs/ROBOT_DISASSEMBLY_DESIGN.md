# 분해 계획에서 로봇 분해 실행까지 — 두 수업의 역할 분리

> 2026-11-06 후속 설명: [현재 구현과 향후 역할 분리](ROBOT_ROLE_BOUNDARY.md)를 함께 읽는다. LLM 작업 판단과 파지·추출·로봇 모션 계산의 경계를 명확히 한 권고안이다. 기존 ASAP 계약은 변경하지 않았으며, 검증 전 순서 후보를 완료 계획으로 취급하지 않는다. 새 로봇 기능/API/실험은 아직 미실행이다.


작성일: 2026-11-06. 상태: **설계 확정 문서 / 새 분해 로봇 기능은 NOT_IMPLEMENTED**.
사용자의 이번 승인은 지침·설계 정리까지다. 운영 코드, 테스트 코드, 환경, 기존 결과는 수정하지 않는다.

## 1. 이번에 정한 목표

같은 기반을 활용하되 두 프로젝트의 산출물을 분리한다.

| 구분 | 이 분해 프로젝트 | 별도 조립 프로젝트 |
|---|---|---|
| 위치 | `C:\dev\disassembly_codex_ready_v2` | `C:\dev\llm-robot-assembly` |
| 수업 목표 | 무엇부터 분해할지 판단하고, 로봇이 잡아 빼서 내려놓는 작업까지 검증 | 주어진 부품을 로봇으로 조립하고 조립 결과를 검증 |
| 분해 모듈의 역할 | 순서·행동 선택, 분해 실행, 실패 경험과 복구 스킬 학습 | 조립 순서를 만드는 데 참고할 분해 순서 후보와 조건을 제공 |
| 실행 책임 | 분해용 로봇 실행기가 잡기·분리·운반·놓기·잔여 조립체 안정성을 확인 | 조립 쪽 실행기가 잡기·운반·삽입·놓기와 조립 완성을 확인 |
| 공유할 것 | 로봇 모델과 검증된 제어·경로계획 기반, 버전이 명시된 데이터 계약 | 순서 제안 모듈의 결과만 소비; 분해 학습 시스템 전체를 가져오지 않음 |

**연구 질문:** 새로운 조립품에서 실제 검증 경험으로 만든 교훈·Python 스킬이 분해 실행의 성공, 복구 비용, 모델 호출 비용에 도움이 되는가? LLM·Memory·Skill이라는 구성요소 자체를 최초성으로 주장하지 않는다.

우선 로봇 시뮬레이션 기반은 조립 프로젝트에 있는 **MuJoCo + UR3e 1대 + 2F-85**를 재사용하는 설계다. ASAP/RedMax와 MuJoCo를 구분한다. 전자는 부품 수준 분리 경로·안정성 근거, 후자는 로봇과 그리퍼를 포함한 실행 검증을 담당한다. Isaac Sim 동시 도입, 실물 제어, 카메라 인식, 임의 OBJ의 자동 물성·조인트 추정은 이번 설계의 첫 구현 범위에 넣지 않는다. 실물 로봇은 후속 별도 단계다.

## 2. 현재 코드가 해 주는 일과 아직 없는 일

### 현재 분해 저장소에서 유지할 기반

- `worker/explicit_action_planner.py::make_explicit_action_planner`: 기존 ASAP 탐색에 명시 행동을 연결하는 어댑터.
- `worker/explicit_action_physics.py::execute_action`: 실제 ASAP/RedMax 검증 연결. 이 PASS는 로봇의 잡기·운반 성공이 아니다.
- `orchestrator/hierarchical_service.py::HierarchicalDecisionService`, `hierarchical_planner.py::SolPlanService`: Luna 탐색, Sol 조건부 계획·재계획, 등록 절차 실행의 기존 연결.
- `orchestrator/explicit_action_memory.py::append_action_observation`, `freeze_memory`, `FrozenActionMemory`: 관측 저장·동결·검색.
- `orchestrator/lesson_memory.py::make_lesson`, `freeze_bundle`: 근거를 가진 교훈과 배포 지식 묶음.
- `orchestrator/python_skill_discovery.py::PythonSkillDiscoveryService`, `python_skill_program.py::evaluate`, `step_program`: 제한된 Python 문법으로 행동을 제안하는 스킬. 임의 Python 실행이나 로봇 직접 제어기가 아니다.
- `orchestrator/learning_cycle_workflow.py::LearningCycleWorkflow`: 단계 산출물·동결·재사용을 묶는 LangGraph. COMPLETE는 분해 또는 스킬 등록 성공과 구분한다.

위 파일이 존재한다고 일반 학습·새 작업 재사용이 안정적으로 완성됐다고 판단하지 않는다. [전체 코드 검토](../SYSTEM_REVIEW_20261106.md)에 남은 실행 경계 문제와 실제 실패가 기록되어 있다.

### 조립 저장소에서 확인한 기반

로봇/그리퍼 모델, TCP 제어, IK, 충돌 검사, 자유공간 경로계획, 조립용 실행·검증·기록이 있다. 보관된 10부품 조립 성공 기록은 **조립 성과**이며 새 분해의 성공 증거가 아니다. 기존 `pick`은 자유 부품을 집고 들어 올리는 절차, `loaded_transport`는 이미 분리되어 들어 올린 부품을 운반하는 절차다.

**새로 필요한 기능:** 조립된 초기 장면, 조립체 안의 부품 잡기, 접촉을 유지하면서 빼는 경로, 분리 완료 판정, 잔여 조립체/지그 검증, 분해 전용 복구, 로봇 실패를 학습 입력으로 바꾸는 연결. 아직 이 저장소에 이식·연결하거나 실행 검증하지 않았다. 상세 [재사용 표](ROBOT_CODE_REUSE_MAP.md).

## 3. 전체 구조와 책임

```text
부품별 CAD + 단위/좌표 + 조립 관계 + 물성 + 지그/목표/예산
             │
             ├─ 순서 제안 모듈 ── 조건부 순서·근거 ── 조립 프로젝트
             │                                      └ 조립 쪽이 실행·검증
             ▼
분해용 관측·의사결정 (동결 Memory/Skill, Luna 탐색 → 필요 시 Sol 계획)
             │   부품·잡기·분리 절차 제안
             ▼
행동 계약 검사 → 경로계획 → MuJoCo 로봇 실행 → 측정 기반 판정
             │                │                   │
             │                └ 실패/불확실 → 재관측·복구·재계획/중단
             └─ 필요 시 ASAP/RedMax 부품 수준 근거 조회
                                                   │
회차 종료 → 실제 경험 → 근거 있는 교훈 → Python 후보 → 검증 → 등록
                                                   │
                                 다음 회차 시작 전 동결하여 재사용
```

이 그림은 **목표 구조**다. 현재 두 저장소를 관통하는 실행 경로가 구현됐다는 뜻이 아니다. 로봇 행동 결정 시 ASAP 후보를 무조건 정답으로 강제하지 않으며, 비교 실험에서는 어떤 순서·관측을 각 방식에 제공했는지 공개한다.

### 상태를 두 군데서 덮어쓰지 않기

1. 기존 ASAP/search adapter는 **계획 탐색 상태**의 유일한 소유자다. DFS/backtracking은 가상 후보를 탐색하는 데 유지한다.
2. 새 로봇 실행기는 **실행 중인 물리 장면의 상태**를 관측하고 소유한다. planner는 행동 요청만 보낸다. 각 요청에 `episode_id`, `action_id`, `state_revision`을 연결한다.
3. 경로계획용 복사 장면은 실행 장면과 분리한다. 계획에서 PASS했다고 실제 부품을 순간 이동하거나 제거 목록에 넣지 않는다.
4. DFS가 이전 노드로 돌아간다는 이유로 실행 중인 조립체를 리셋하지 않는다. 실제 되돌림이 필요하면 그 동작 자체를 계획·실행·검증한다. 회차 재시작은 새 회차로 비용과 실패를 남긴다.
5. LangGraph는 수명주기·호출 예산·산출물을 묶는다. 두 상태의 또 다른 소유자가 되지 않는다.

### 로봇 동작의 단계와 성공 기준

| 단계 | 필요한 관측/확인 | 실패했을 때 |
|---|---|---|
| 초기 상태 확인 | 등록된 CAD·단위·좌표·물성, 지그, 잔여 부품, 안정된 조립 상태 | 입력 오류/불안정 상태를 기록하고 실행 보류 |
| 접근·잡기 | IK/관절 한계, 팔·손가락 충돌, 실제 접촉과 잡은 부품의 상대 자세 | 아직 제거하지 않은 상태로 재관측, 허용된 재접근만 수행 |
| 분리 이동 | 조립 관계에 맞는 이동, 허용된 접촉, 파지 유지, 잔여 조립체 안정 | 실제 측정된 실패만 기록; 충돌 원인/끼임을 추측하지 않음 |
| 분리 완료 | mating/끼워짐 관계 해제, 대상이 조립체에서 충분히 분리됨, 파지 유지 | 단순 TCP 이동량으로 성공 판정하지 않음 |
| 운반·놓기 | 팔·그리퍼·운반 부품의 충돌, 목표 트레이 위치, 놓은 뒤 지지·안정 | 떨어뜨렸거나 위치 미확인이라면 완료 처리하지 않음 |
| 회차 완료 | 요청한 부품들이 실제 제거·배치됨, 잔여 조립체와 로봇 상태 확인 | 부분 완료와 전체 완료를 구분 |

임계값은 제품 치수·장면 설정과 연결해 다음 구현 단계에서 명시한다. 조립용 위치 오차 임계값을 분리 판정에 복사하지 않는다. 시뮬레이션 ground truth를 이용한 관측임을 기록하고 실물 센서 관측처럼 표현하지 않는다.

### 한 대의 로봇과 지지 조건

ASAP에서 지정한 여러 지지 부품은 실제 지그나 로봇 팔의 존재를 증명하지 않는다. 한 UR3e가 대상 부품을 잡는 동안 다른 부품을 별도 손으로 지지한다고 가정하지 않는다. 첫 장면은 고정 베이스/지그가 명확한 구조를 사용한다. 지그 변경·조립체 뒤집기는 공짜 상태 변경이 아니라 별도 실행 절차 또는 사람 개입으로 기록한다. 지원하지 않는 자세/지지 요구는 `UNSUPPORTED` 사유로 보류한다.

## 4. 실패·fallback·경험·스킬

### fallback

- 계획 단계에서 저비용 모델이 유효한 진전을 못 내면 근거와 남은 예산을 갖고 상위 계획 모델로 넘긴다. 승격 조건/최대 호출은 실행 프로필에 명시한다.
- API 실패나 응답 오류를 정상 모델 판단으로 세지 않는다. 기존 canonical 순서 fallback은 기존 **계획 경로**에 보존한다.
- 로봇 동작 중 상태가 불확실하면 임의 부품·순서 fallback으로 계속 움직이지 않는다. 상태 확인과 사전 검증된 중단/복구 절차를 우선한다. 같은 명령 자동 재전송은 하지 않는다.
- 기존 `recovery_support_guard`의 지지 해제 제한은 의도된 정책이다. 새 로봇 프로필에서 지그/지지 변경을 구현하기 전 그 검사를 제거하지 않는다.

### 경험과 교훈을 분리해 저장

기존 기록은 그대로 두고 새 버전/별도 저장 공간을 사용한다. 다음 정보는 새 관측의 필수 설계 항목이다.

| 종류 | 저장할 내용 |
|---|---|
| 관측 사실 | 제품·부품 대응, 장면/mesh hash, 단위, 로봇/그리퍼/지그, pose, 요청 행동, 원시 센서/시뮬레이션 근거 참조 |
| 판정 | `evidence_domain`(부품 검증/로봇 시뮬레이션/실물), verifier·설정·코드 버전, PASS/REJECTED/UNKNOWN/ERROR, 관측된 실패 단계 |
| 회차 수락 | 원시 물리 결과와 별도의 `accepted_for_transition`, 실행/허용 시간, `deadline_exceeded`, 전후 상태 revision |
| 교훈 | 적용 조건, 출처 evidence ID, 관측으로 뒷받침되는 설명, 미확인 원인/가설의 구분, 검증 범위 |
| 스킬 | Python source/hash, 호출 가능한 행동 계약, 적용/보류 조건, 검증 회차/조건/실패, 지원하는 verifier 도메인 |

현재 `explicit_action_memory` 형식에 이 필드가 모두 존재한다고 가정하지 않는다. 조립의 `experience_memory` 또한 첫 삽입 과제에 한정된 형식이므로 기존 JSON을 그대로 합치지 않는다. 과거 불완전한 기록은 원본을 보존하고 누락 정보를 unknown으로 명시한다.

### 스킬은 실제로 무엇인가

두 층을 구분한다.

1. 개발자가 검증할 기본 로봇 기능: 접근, 잡기, 제한된 분리 이동, 관측, 운반, 놓기. 실제 제어·접촉 판정은 이 함수들이 맡는다.
2. 모델이 경험에서 만드는 Python 복구 절차: 관측 조건을 읽고 위 기능의 후보·파라미터·실행 순서를 제안한다. 임의 MuJoCo 상태 변경, 파일/네트워크 접근, verifier 수정 권한은 주지 않는다.

기존 Python VM의 제한 문법·유한 실행·버전·검증 원칙을 유지하고 **로봇 행동용 문맥/계약을 별도로 추가**한다. 현재 VM이 반환하는 ASAP 행동을 곧바로 로봇 명령으로 실행하지 않는다. 부품 경로에서 검증된 스킬은 로봇용으로 자동 승격하지 않는다.

후보 → 문법/계약 검사 → 조건별 실제 시뮬레이션 → 미검증 범위 표시 → 등록 → 다음 회차에 동결한 순서로 운영한다. 실패한 후보도 보존한다. 한 조건의 성공은 provisional이며 범용 복구 성공으로 보고하지 않는다. 평가 중에는 장기 지식을 수정하지 않고 현재 episode 로그만 쌓는다.

## 5. 첫 구현 범위와 단계별 완료 조건

다음은 **향후 작업 순서**다. `sequence_only`, `robot_disassembly_sim`은 제안 프로필명이며 현재 CLI 옵션이 아니다.

| 우선순위 | 작업 | 완료를 인정할 증거 |
|---|---|---|
| R0 | 두 저장소 사이 계약·부품 ID·단위·좌표·출처 변환, 로봇 기반의 버전 고정 | 작은 저장 입력으로 정상/부분/잘못된 결과를 구분. 원본 결과 무변경. 새 API 불필요 |
| R1 | 조립 로봇 기반을 별도 분해 모듈로 이식, 작은 조립 상태 장면 구성 | 한 고정 베이스와 제거 가능한 1~2부품으로 초기 상태 안정성·접근·파지·분리·놓기를 실제 MuJoCo에서 확인. 우선 scripted 동작임을 표시 |
| R2 | 분해 전용 관측·분리/잔여 안정성 검사·실패 시 보류와 복구 | 잡기 실패·경로 불가·미분리·낙하·상태 불일치를 완료로 처리하지 않음. 실패 테스트는 자연 발생/시험 주입을 별도 표시 |
| R3 | LLM 계획과 로봇 실행 연결, 관측→교훈→Python→검증→등록→다음 실행 | 강제 스킬 선택 없이 적용 여부·실행 여부·실제 복구를 분리 기록. 과거 실패와 같은 행동 반복 방지. 유료 시험은 별도 예산 확정 후 |
| R4 | 학습 제품/평가 제품을 나누고 동결 지식 효과 비교 | 동일 로봇·장면·관측·실행기·물리 예산에서 성공/제거/복구/시간/API·준비 비용 비교. 새 제품 성능과 같은 제품 반복 효과 분리 |
| R5 | 실제 UR3e/2F-85 분해 검증 | 대상·지그 제작, 좌표/TCP/힘·속도 설정, 센서/중단 절차, 실험 권한 확인 후 별도 진행 |

첫 로봇 시험 제품의 **제안**은 조립 프로젝트의 프레임 CAD를 축소한 단순 부품 관계다. 기존 10부품 구조의 생성기가 있으나 조립 완료 상태의 분해 장면을 자동 제공하지는 않는다. 구체적인 부품 조합·고정 방식·치수는 R1 입력 검사를 통과한 뒤 정한다. 부품 15~20개 ASAP 제품을 즉시 로봇 실험 대상으로 정하지 않는다. 로봇이 잡을 수 있는지, 지그가 있는지 먼저 확인해야 한다.

시간은 새 로봇 장면/접촉 조건을 확인하기 전 확정하지 않는다. R0는 작은 구현 단위, R1·R2가 가장 큰 기술 불확실성이다. 각각 끝날 때 측정한 결과와 다음 단위의 예상 시간을 다시 보고한다.

## 6. 기존 시스템 검토에서 반드시 반영할 항목

[SYSTEM_REVIEW_20261106.md](../SYSTEM_REVIEW_20261106.md)의 F1/F2/F4는 새 학습 통합 전에 해결 여부를 확인한다.

- F1: 일반 학습과 재검증의 시간 의미를 통일. 과거 관측 허용시간과 새 검증 예산을 별개로 보존한다.
- F2: 물리 PASS와 회차 내 수락·마감 정보를 분리해 보존·검색한다.
- F3: 직접 스킬 선택과 자동 복구의 지지 변경 권한 차이는 이미 계획 입력에 설명된다. 중복 설명 기능을 새로 만들거나 의도된 검사를 삭제하지 않는다.
- F4: 누적 스킬 전체를 무조건 넣지 않고 적용 조건·도메인·입력 한도에 맞춰 제한된 집합을 제시한다. 탈락한 스킬/검색 근거를 기록한다.

위 문제가 고쳐졌다고 이번 문서에 쓰지 않는다. 기존 실행기 전체를 한꺼번에 교체하지 않고, 새 지원 프로필에서 일반 진입점부터 검증·등록·배포까지 같은 입력 계약을 사용하게 한다.

## 7. 비교와 보고

ASAP/RedMax의 전체 계획 성공과 로봇의 실제 분해 완료를 같은 지표로 합치지 않는다.

- 부품 계획 비교: 기존 ASAP heuristic/GNN 설정과 현재 선택 방식을 같은 부품 수준 검증기·예산으로 비교. 가중치/학습 split은 확인한 사실만 기록.
- 로봇 실행 비교: 모든 조건에 같은 로봇 실행기·검사·지그를 사용하고 순서 또는 선택 정책을 바꾼다. ASAP 후보를 로봇에 적용한 경우도 로봇에서 실제 검증한 결과를 따로 집계.
- Memory/Skill 효과: LLM만 / LLM+Memory / LLM+Memory+Skill 및 동일 정보 deterministic 방식. 비용·준비 회차 포함. 단일 회차 성공은 우월성 증거가 아니다.

이번 정리는 설계만 완료했다. API 0회, 새 물리시험 0회, 새 로봇 분해 성공 0건이다. 다음 작업은 R0와 R1의 작은 단위이며, 이번 문서 자체는 코드 수정·새 API·실물 실행 승인이 아니다.
