# 매 회차 뒤에 다시 배우는 순서 학습 — sequence_iterative_learning_v1

작성일: 2026-11-10. 기존 두 회차 학습 코드를 보존하고, **제품당 최대 5회까지 반복하되 첫 2회 결과에서 반드시 멈춰 검토하는 새 경로**를 준비한다. 이 문서의 API 숫자는 새 유료 실행 제안이며 실행 승인이나 실제 사용량이 아니다. 실제 모델을 사용한 새 반복 학습의 결과는 아직 `NOT_RUN`, 효과는 `UNVERIFIED`다.

## 1. 이전 흐름에서 무엇이 달라지는가

기존 흐름은 첫 회차에서 경험을 만들고 스킬을 학습한 다음, 두 번째 회차에서 재사용을 확인했다. **두 번째 회차 뒤에는 같은 제품에 대한 새 학습 단계가 없었다.**

새 흐름은 매 회차를 끝낼 때마다 새 경험을 포함해 교훈과 Python 후보를 다시 만든다. 두 번째 회차와 마지막 다섯 번째 회차도 학습을 생략하지 않는다.

| 구분 | 기존 두 회차 경로 | 새 반복 학습 경로 |
|---|---|---|
| 자유 분해 | 제품당 2회 | 제품당 최대 5회 |
| 학습 시점 | 첫 회차 뒤 | **매 회차 뒤**, 2·5회차 포함 |
| 최초 실행 단위 | 5제품 × 2회 | 5제품 × 2회까지만 먼저 실행 |
| 다음 진행 | 해당 경로 종료 | 결과 검토·별도 승인 후 3~5회차 가능 |
| 무제한 성공 반복 | 없음 | 없음 |
| 모델 가중치 업데이트 | 없음 | 없음 |

여기서 학습은 파인튜닝이 아니다. 모델 밖에 **관측 메모리, 근거가 있는 교훈, 검증된 제한 Python 순서 스킬**을 저장하는 것이다. 재사용이 실제로 늘어나는지, 비용이 줄어드는지는 아직 검증해야 한다.

## 2. 회차 한 번의 구조

1. **동결:** 현재까지 모은 메모리·교훈·등록 스킬을 새 회차용 파일로 고정한다. 회차 진행 중 장기 라이브러리를 몰래 바꾸지 않는다.
2. **자유 분해:** Sol이 부품 후보 전체의 시도 순서를 정하거나 호환 순서 스킬을 선택한다. 원래 ASAP이 DFS·자세·방향·지지 탐색을 하고 RedMax가 부품 수준 물리를 검사한다.
3. **관측 저장:** 전체 성공/실패와 별개로 실제 시도 근거를 보존한다. 경로/안정성의 원시 결과, 시간 내 수락 여부, 제품·설정·소스·입력 해시를 연결한다.
4. **교훈:** Luna가 새 관측과 누적된 근거에서 초기 교훈을 작성한다. 최대 1호출이다.
5. **Python 후보:** Luna가 순서를 제안하는 제한 Python을 생성한다. 실패 피드백에 따른 수정 후보까지 **합계 최대 2호출**이다.
6. **후보 검증:** 후보마다 같은 제품의 seed 0·1 조건에서 원래 ASAP/RedMax로 전체 연결 분해를 검증한다. **검증에는 모델을 호출하지 않는다.** 최대 2버전 × 2조건 = 4회이며 첫 실패에서 후속 검증을 생략할 수 있다.
7. **검증 후 교훈:** 등록 조건을 통과한 후보에 대해 새 검증 근거를 반영해 교훈을 갱신한다. 최대 1호출이다.
8. **등록·동결:** 코드·입력·원시 결과·증명 해시를 다시 검사해 조건부 등록하고 다음 회차 전 동결한다. 실패한 후보와 거절 이유도 남긴다.

관측이 없거나 교훈·후보가 유효하지 않으면 해당 후속 단계를 건너뛰고 이유를 남긴다. 물리 실패를 성공으로 바꾸기 위해 후보를 강제 등록하지 않는다. 후보 검증에서는 검증하려는 코드를 직접 실행하지만, **다음 자유 분해에서는 모델에 스킬 선택을 강제하지 않는다.**

같은 제품의 두 seed를 통과했다는 것은 해당 조건에서의 잠정 등록 근거다. 새로운 제품으로의 일반화나 스킬 없는 정책보다 나은 성능의 증거가 아니다. 마지막 다섯 번째 회차에서 새 스킬이 등록되더라도 여섯 번째 분해를 자동으로 추가하지 않는다. 그 스킬의 다음 자유 실행 재사용은 이후 승인된 작업에서 확인한다.

이 경로에서 Python 스킬은 현재 부품 후보의 **완전한 순열**을 만든다. 로봇 grasp, 관절 궤적, 힘 제어를 생성하는 기능이 아니며 물리검증 결과를 재사용해 검사를 건너뛰지 않는다. 원래 ASAP의 마지막 두 부품 질량·고정 베이스 규칙도 유지한다.

## 3. 첫 2회에서 멈추는 검토 단계

최초 단계 `initial`은 5개 학습 제품의 1~2회차, 합계 **10회차와 10번의 회차 후 학습**까지만 포함한다. 구현은 **5제품의 1회차를 순서대로 마친 뒤 5제품의 2회차를 진행**한다. 각 회차 후 학습 결과를 누적하므로 뒤에 오는 다른 학습 제품에도 앞선 경험을 제공할 수 있다. 각 제품의 2회차 후 학습·등록 결과를 저장하고 검토를 위해 멈춘다.

3~5회차는 별도 `continuation` 단계다. 다음 조건을 새 실행기에서 확인해야 하며, 예산 계산 함수가 대신 승인하지 않는다.

- 최초 단계의 원본 체크포인트와 동결 지식·데이터셋·코드 출처를 확인한다.
- 최초 결과의 실패, 미확정 호출, 비용, 등록·선택·실행 현황을 검토한다.
- 계속 실행할 범위를 명시한 별도 승인과 검토 후 계속하기 옵션을 요구한다.
- 원본 실행 폴더를 덮어쓰거나 실패 회차를 자동 재실행하지 않는다.

예산 모듈의 `full`은 25회차 전체의 **비용/시간 합계 표시용**이다. `validate_stage_request`는 `full`을 실행 단계로 받지 않는다. 따라서 전체 합계 값을 이용해 첫 검토 단계를 건너뛰지 않는다.

## 5. API 예산: 최초 실행과 계속 실행을 분리

회차 한 번의 상한은 **Sol 25회/$4.00 + Luna 4회/$0.10 = 29회/$4.10**이다. Luna 4회에는 초기 교훈1, 후보·수정 합계2, 검증 후 교훈1이 모두 들어 있다.

| 범위 | 자유 회차/회차 후 학습 | Sol 최대 | Luna 최대 | 총 호출 | 프로그램 비용 상한 |
|---|---:|---:|---:|---:|---:|
| 최초 1~2회차 | 10/10 | 250 | 40 | **290** | **$41.00** |
| 검토 후 3~5회차 | 15/15 | 375 | 60 | **435** | **$61.50** |
| 전체 합계, 실행 단계 아님 | 25/25 | 625 | 100 | **725** | **$102.50** |

기존 두 회차 제안인 270회/$40.50과 다른 이유는 **두 번째 회차 뒤에도 학습을 수행하기 때문**이다. 이전 제안 숫자를 현재 구조의 상한으로 계속 사용하지 않는다. 최초 단계의 승인만으로 추가 435회/$61.50을 사용할 수 없다.

자동 HTTP 재시도·실패 회차 자동 재실행은 각각 0이다. 호출/비용은 유한한 숫자로 검증하며, 음수·NaN·Infinity·불명확한 문자열·상한 초과 값·bool을 허용하지 않는다. 호출을 많이 허용했다는 사실과 성공 보장은 다르다.

Endpoint는 `https://api.openai.com/v1/responses`다. 단가는 2026-11-10 공식 모델 문서로 확인한 기존 설정값을 사용한다.

| 모델 | 입력/출력 100만 토큰당 | 본문 byte 상한 | 출력 토큰 상한 | 최대 요청의 보수적 예약 |
|---|---|---:|---:|---:|
| GPT-6.1 Sol | $2 / $10 | 65,536 | 2,048 | $0.155648 |
| GPT-6 Luna | $0.10 / $0.50 | 131,072 | 4,096 | $0.01536 |

출처: [GPT-6.1 Sol 공식 모델 문서](https://developers.openai.com/api/docs/models/gpt-6.1-sol), [GPT-6 Luna 공식 모델 문서](https://developers.openai.com/api/docs/models/gpt-6-luna). 표준·짧은 문맥 단가이며 캐시·Batch·Flex 할인은 가정하지 않았다.

예약 계산은 `본문 UTF-8 byte 수 상한 + 요청 여유 2,048`을 입력 토큰의 보수적 추정값으로 쓰고 출력 상한을 더한 것이다. 실제 공급자 청구 토큰과 같지 않다.

- 최초 단계의 최대 크기 기준 예약 합계: **$39.5264**.
- 추가 단계: **$59.2896**.
- 전체 합계: **$98.8160**.

이는 실제 청구액이나 이번 배치의 예상 사용량이 아니다. 이전 한 제품의 평균 비용을 그대로 새 반복 학습의 확정 비용으로 제시하지 않는다. 호출 실패·중단 시 실제 사용량과 남은 예약은 로그로 확인한다.

## 6. 물리검증·시간 상한

물리 기준은 그대로 유지하고 회차 수만 유한하게 늘린다.

| 종류 | 회차당 경로·안정성·복합 시도 상한 | 본 실행 시간 | 외부 종료 시간 |
|---|---:|---:|---:|
| 자유 분해 | 각각 256 | 60분 | 65분 |
| 후보 검증 | 각각 128 | 10분 | 11분 |

한 학습 회차에서 후보 검증은 최대 4번이다. 실제 실패·등록 결과에 따라 더 적게 실행할 수 있다.

| 범위 | 자유 분해 최대 | 후보 검증 최대 | 각 검사 종류의 합계 상한 | 본 실행 제한 합계 | worker 외부 timeout 설정 합계 |
|---|---:|---:|---:|---:|---:|
| 최초 단계 | 10 | **40** | 7,680 | 16시간 40분 | **18시간 10분** |
| 추가 단계 | 15 | 60 | 11,520 | 25시간 | **27시간 15분** |
| 전체 | 25 | **100** | 19,200 | 41시간 40분 | **45시간 25분** |

표는 개별 worker의 timeout 설정을 합한 것이며 **전체 배치 벽시계 시간의 상한이나 예상 소요 시간이 아니다.** worker 밖의 Luna API 호출, 호스트 파일 검사·기동·정리와 강제 종료 유예가 별도로 들어간다. 후보가 일찍 실패하거나 등록 조건을 만족하지 못하면 후속 검증을 생략한다. 별도의 SDF 선생성은 하지 않았으므로 실제 첫 장면 준비 비용도 관측해야 한다. 이전 5~8시간 추정이나 14.5시간 외부 상한은 **이 새 반복 구조의 시간 약속으로 사용할 수 없다.**

## 7. 현재 구현 근거와 보고 방식

새 예산 모듈은 `orchestrator/sequence_iterative_budget.py`다.

- `stage_budget`: 최초/추가 단계의 호출·비용·물리·시간 상한을 계산한다. `full`은 요약만 반환한다.
- `role_reservation`: 현재 설정 단가와 본문·출력 상한의 보수적 예약을 계산한다.
- `validate_stage_request`: 실행 가능한 단계와 유한한 수치 상한을 검사한다. 승인·체크포인트 검증을 했다는 뜻이 아니다.
- `build_budget_proposal`: 이전 데이터셋 manifest 해시를 연결한 비활성 제안을 만든다.

`tests/test_sequence_iterative_budget.py`의 9개 검사는 통과했다. 파일·환경 키·모델·프로세스·물리에 접근하지 않는 순수 계산 검사이며, 실제 모델이나 실제 분해의 성공을 입증하지 않는다. 명령과 로그는 `runs/sequence_iterative_prepare_20261110/budget_tests/`에 있다. 제안 원문은 같은 run의 `budget_proposal.json`이다.

새 실행기 관련 소스도 다음과 같이 연결한다.

- `tools/run_sequence_iterative_training.py`: `IterativeBackend`, `current_round_packet`, `IterativeLearningService`, `main`. 회차마다 기존 native 실행·학습 기능을 새 예산 장부로 연결하고, 현재 회차 근거를 교훈 입력과 인용 검사에 포함한다.
- `orchestrator/sequence_iterative_training.py`: `run_iterative_training`. 제품 5개를 회차별로 순회하고, 2회차 후 `REVIEW_REQUIRED`에서 멈춘다. 학습 단계 완료와 실제 전체 분해 성공을 같은 의미로 취급하지 않는다.
- `orchestrator/sequence_training_checkpoint.py`: `make_checkpoint`, `load_checkpoint`, `claim_continuation`. 출처와 해시를 확인한 체크포인트에서 새 실행으로 이어가며, 같은 체크포인트의 중복 계속하기를 차단한다.

새 실행기는 기본적으로 준비만 수행한다. `--stage continuation`은 체크포인트를 요구하고 실제 호출에는 별도로 `--continue-after-review`와 `--allow-live-api`가 필요하다. 플래그 자체는 사용자 승인 기록을 대신하지 않는다. 체크포인트의 제품·source·예산 프로필이 달라졌다면 예전 결과를 그대로 이어 실행하지 않는다.

반복 진행·체크포인트 중단·계속하기의 통합 검사 결과는 최종 `IMPLEMENTATION_STATUS.md` 및 해당 run 보고서를 따른다. 위 경로가 소스에 존재한다는 사실과 실제 5제품 배치가 성공했다는 사실을 구분한다. 이전 Beam의 실제 물리 + injected 모델 출력 시험은 이전 연결의 근거이며, 이번 5제품 반복 학습의 실제 모델 시험으로 합산하지 않는다.

검토 시에는 다음을 따로 집계한다.

1. 실제 새 관측과 근거 있는 교훈이 증가했는가.
2. 코드 후보가 생성·수정되었으며 실제 조건별 검증을 통과했는가.
3. 중복 코드로 등록 개수를 부풀리지 않았는가.
4. 다음 자유 분해에 스킬이 제공·선택·실행되었는가.
5. 전체 연결 분해와 검사 횟수·시간·비용이 어떻게 변했는가.
6. 실패·미선택·미실행·미확정 요청이 숨김없이 보존됐는가.

동일 제품을 반복해 성공한 결과와 처음 보는 제품에 도움이 된 결과는 다르다. 최초 단계 후 검토에서 다음 진행의 가치와 원인을 판단하고, 최종 라이브러리를 동결한 뒤에 새 제품 평가를 설계한다. **코드 연결 완료, 등록 완료, 재사용 관측, 성능 개선 증거를 구분한다.**
